# Current implementation: L4 performance

The full six-implementation comparison was rerun on the implementation after
the dispatch/indexing and metadata-check changes. The measured source is
`7361cfb93cb9f08ac8b40013e4da782200a86bb1`; its library and CUDA implementation
are unchanged from main `983c19cb2db29b3ecfc0f7a92f9b68477f7bc159`.

**Both full runs passed, and no package/adapter-to-HF latency comparison
exceeded the investigation threshold in both processes.** Encoder timings
were within about 2% of HF. Short training timings varied substantially, so
these results do not establish a fixed speedup or universal performance parity.

## Evidence and conditions

- [First run 36227885287](https://github.com/S-aiueo32/torch-ms-deform-attn/actions/runs/36227885287):
  all 54 common-policy backend/shape/dtype configurations passed output and all
  three gradient checks; all 486 timing rows are present; Pod deletion verified.
- [Fresh-process repeat 36229194694, attempt 2](https://github.com/S-aiueo32/torch-ms-deform-attn/actions/runs/36229194694/attempts/2):
  the same 54 correctness configurations and 486 timing rows passed; source
  revision and competitor source hashes match the first run; Pod deletion verified.
- [Attempt 1](https://github.com/S-aiueo32/torch-ms-deform-attn/actions/runs/36229194694/attempts/1)
  timed out waiting for an SSH endpoint before running the workload. Its Pod
  deletion was verified; it supplies no performance evidence.

Both runs target the same source and use the existing randomized-order harness:
three shapes, FP32/FP16/BF16, forward/backward/forward+backward, three repetitions,
five warmups, and one-second minimum timing windows. Competitor revisions and
the HF baseline `abfd4042216fa4f84c9c5c4e3e844a3143c70ad5` are pinned. The
common policy computes in FP32 and includes casts for low-precision inputs.
Default CUDA metadata-content checking is disabled in the package and adapter;
shape, device, dtype, and indexing-range guards remain in place.

Both successful runs used NVIDIA L4, driver 595.91.07, AMD EPYC 9254,
Python 3.11.16 and PyTorch 2.10.0+cu126. The adapter is the Kernel Builder
0.16.1 CMake development build, not the locked Nix distribution. Timings are
eager operator wall latency; they do not measure compiled model throughput.

Each successful Actions artifact, `cuda-runpod-RUN_ID-ATTEMPT`, contains the raw
report at `artifacts/benchmark-kernel-hub.json`, pinned sources, upstream and loaded
artifact hashes, dependency versions, Phase 1 logs, CUDA test logs, and
`runpod-state.json`. Generated evidence stays in Actions, not in this source
tree. Reproduce the tables with:

```bash
python kernel-hub/benchmarks/summarize.py PATH/TO/artifacts/benchmark-kernel-hub.json
```

## HF comparison and repeat investigation

One of the first run's 54 package/adapter-to-HF comparisons crossed the
investigation threshold: adapter decoder BF16 forward+backward, 0.3171 ms versus HF 0.2396 ms
(1.323×). The fresh-process repeat did not reproduce it: adapter 0.3119 ms
versus HF 0.3506 ms (0.890×). The adapter median stayed near 0.31 ms while
HF's median changed; no implementation change occurred between these runs.

The repeat flagged zero of 54 comparisons. Flags require a latency increase
greater than both 5% of HF and twice the larger summarized IQR. These are
investigation flags, not statistical confidence bounds.

Selected wall-latency ratios to HF, comparing identical precision policies:

| Implementation / case | First run | Repeat |
| --- | ---: | ---: |
| Adapter decoder FP16 forward+backward | 0.627× | 0.964× |
| Adapter decoder BF16 forward+backward | 1.323× | 0.890× |
| Package decoder FP16 forward+backward | 1.163× | 0.708× |
| Adapter encoder FP32 forward | 1.018× | 1.018× |

The package decoder FP16 first-run ratio did not cross the IQR-based threshold.
For the flagged adapter BF16 case in the first run,
adapter repetition medians were 0.2203, 0.3171 and 0.4041 ms; HF medians were
0.2325, 0.3794 and 0.2396 ms. The slower adapter windows had only three timing
samples. In the repeat, adapter medians were 0.2178, 0.3381 and 0.3119 ms;
HF medians were 0.4059, 0.3506 and 0.3222 ms. Several windows again had only
three or four samples. The variation must not be hidden behind a single ratio.
The reports do not isolate its cause or provide a stable ranking for short
training workloads. Longer sampling windows and profiling would be needed
before making a specific short-training speedup claim.

Encoder package/adapter ratios across all dtypes and modes were 0.994–1.018×
HF across the two runs. Incremental encoder forward+backward allocation matched
HF in both:
37.1875 MiB for FP32 and 69.0625 MiB for FP16/BF16.

All 18 native low-precision competitor configurations in each run were excluded
from timing: 12 failed the independent FP64 accuracy gate, and six MMCV/Triton BF16
cases were unsupported. This is specific to the recorded accuracy contract;
it does not establish that native low precision is unsuitable for every use.
No numerical tolerances or CUDA arithmetic were changed for this rerun.

Before timing in each successful run, Phase 1 passed 3/3, CUDA tests passed
11 tests and 167 subtests with two expected skips, and CUDA Graph tests passed three tests and 25
subtests. The skips require a second GPU or a CPU-only build. The benchmark
task does not rerun the 20-case RT-DETR model matrix.

The historical six-backend run used 0.2-second windows and a different driver
and preceded the implementation changes. Do not combine its absolute timings
with these runs to claim an isolated optimization speedup.
